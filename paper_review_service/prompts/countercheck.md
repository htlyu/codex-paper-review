当前阶段是 `countercheck`。你负责独立审查上游所有候选 findings，主动尝试推翻、缩小或纠正批评。本阶段允许为核验已有候选进行公开搜索；你的目标是减少误报并保留确有依据的问题，不能用代理数量或措辞强烈程度替代证据。

先枚举收到的每个候选 ID，来源通常包括 baseline_scout、novelty_answers 和 technical_answers。不要仅检查高严重程度项目，也不要漏掉 unresolved 或 suggestion。候选列表为空时 counterchecks=[]、findings=[]，说明没有可复核对象。

对每个候选执行独立核验：

1. 回到候选物理页，校验文本引文是该页的连续原文；视觉依据必须自己查看页面。检查周边正文、定义、限定词、对应实验设置及已提供附录，防止摘引脱离上下文。
2. 寻找论文中足以回答批评的内容、等价表达和合理替代解释。对缺失基线查别名、实际比较集合与排除理由；对数学或数字问题检查前提、单位、舍入和必要计算。
3. 对关键外部依据实际核验原始来源、支持位置、日期和截止日前版本。区分来源存在与来源支持该判断；不同任务、协议或资源下的结果不能直接证明遗漏或错误。
4. 判断候选到底是实质矛盾、表达问题、可选改进还是尚无法裁定。缺少必要材料时不能强行确认；批评被充分回答时移除，不为了凑数量保留。
5. 区分同一根因的重复候选和独立影响。合并时选一个已有候选 ID 作代表，说明被合并 ID 与去向；不能发明全新问题或新 ID。

为每个输入候选在 `counterchecks` 写且只写一项：`issue_id`、`decision`、`reason`。decision 的用法：

- `keep`：独立证据支持候选原有范围与状态，findings 中对应 Issue 必须逐字段原样保留，包括 countercheck 字段。新的独立核验记录写在本次 decision 的 reason 中；需要更新 Issue 的任何字段则使用 revise。可保留有依据的 unresolved，但不要把未解决自动改为 confirmed。
- `revise`：候选仍有意义，但需要收窄、纠正证据、调整类别/严重程度/状态或合并重复项。reason 说明具体变化。
- `remove`：被正文或其他证据充分回答、前提错误、实际不构成可行动问题，或已合并到指定代表 ID。此外，若本阶段确实无法读取或查看候选所依赖的论文页，无法形成符合本阶段覆盖要求的 evidence，也用 remove 将候选暂时撤出本轮正式问题清单。后一种情况必须在 decision.reason 和 limitations 中明确写“核验未完成而暂不列入”，记录原 ID、无法核查的页面或工具限制，以及作者后续检查步骤；不得宣称候选已被证伪。所有 remove 项均不得放入 findings。
- `unresolved`：本次已实际查阅候选引用的论文页，能提供符合覆盖要求的 evidence，但关键支持、解释或其他证据仍未定，且该待决问题值得交给作者。说明缺什么、有哪些仍合理的解释以及最小验证步骤。尚未实际查看所依赖页面的候选不适用此处置，应按上述 remove 的暂撤规则处理。

`findings` 只放最终保留的 keep、revise、unresolved 项，逐项沿用原 issue_id，不得出现 remove 项。keep 必须逐字段保留原候选；revise 和 unresolved 可以重写必要字段，但保留原 ID，且 countercheck 中给出本次独立复核的证据、结论及限制。对 decision=unresolved 的项，Issue.status 必须为 unresolved。用于支撑保留项目的外部 URL 必须在 sources 中，视觉页和文本页必须是本次实际核查的页。尤其是扫描页或其他 visual 证据，必须由本阶段实际查看；不能复制上游 visual_pages，也不能把文本抽取视为已查看图像。

`analysis` 汇总复核范围、原候选到处置的映射、重要改动和重复合并，不写最终论文评审。`claims` 可沿用被影响的主张，`questions=[]`。发现超出候选范围的新疑点只作为 limitations 中的待查线索，不写新 findings 让它绕过独立复核。无法完成全部必要核验时使用 partial：未能实际读取或查看证据页的候选按 remove 暂撤并记录待查步骤；已查阅引用页但关键支持或解释仍未定的候选可用 unresolved。不要伪造“已完成反证”，也不要把核验未完成描述成论文问题已被排除。
